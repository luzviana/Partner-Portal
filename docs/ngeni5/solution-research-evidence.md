# Partner Portal build versus buy assessment v1

Date: 2026-10-06. Author: EA review agent. Audience: Partner-Portal coordinator, EA owner, Commercial, Security and Platform owners.

This is research and a proposed selection method, not a procurement decision or authorization to implement. It supplements the [commit-bound EA review](https://github.com/luzviana/ngenious-enterprise-architecture/blob/5b9fc35daad180e05ee564eb80bbf16eff6124bb/reviews/partner-portal/2026-10-06/review-v1.md) of Partner-Portal PR #1 at `a54a14d0a161991425394fce3f960b4a62330384`. The five independent business services and retention of HubSpot are user requirements. Vendor claims below come from primary documentation checked on this date; they are not results from a licensed account, customer environment or proof of concept. Prices, existing entitlements, reseller rights and negotiated terms have not been verified. Unknowns must remain unknown until demonstrated.

## Recommended investment direction

Retain the existing SSO and HubSpot capabilities. Buy specialist planning/discovery where a supported handoff and isolation model pass the gates below. Build the domain-specific multisite composition and thin integration contracts when candidate products cannot demonstrate those semantics. Compare a commerce framework and a purchased channel marketplace before committing to a completely custom Marketplace. Compare HubSpot quoting, a HubSpot-integrated commercial quoting product and an independently operated quote engine on the same cases. An existing CRM is a reason to test its commercial capabilities first, not evidence that it already supplies technical configuration, partner authorization or the required proposal experience.

Prefer managed operation for commodity runtime and inference if the approved platform, region and data policies fit. A managed service still needs application authorization, protected data boundaries, incident ownership, recovery and an exit plan. No evidence currently establishes a complete off-the-shelf fit for all five services.

## Selection rules

First apply pass/fail gates: authorized partner/customer/solution isolation; approved SSO or an explicitly accepted bounded exception; native standalone access; supported versioned API or reviewed export/import; legal rights for the intended users and embedding/redistribution; field ownership; data portability and deletion; and an accountable operator. A low price cannot compensate for a failed gate.

For candidates passing those gates, score only demonstrated evidence: workflow fit 30%, integration and data fidelity 25%, three-year total cost 20%, operating/recovery fit 15%, and exit cost 10%. Security/isolation remain gates, not tradeable weighted points. Record evidence as documented, demonstrated, contractually confirmed, unknown or failed. Do not give an unknown a passing score. Commercial and Product should ratify the weights before procurement.

## Marketplace and commercial catalog

**Thin custom application:** best control over portfolio-specific comparisons, partner eligibility, saved selections and handoff. It also makes ngenious responsible for catalog stewardship tools, search, imports, entitlement administration, publication, pricing confidentiality and support. PostgreSQL and a UI are building blocks, not a finished marketplace. Prefer this route only if the pilot is deliberately browse/select/quote and the alternatives add more operating or integration burden than they remove.

**Medusa as a commerce foundation:** the documented Product and Pricing modules cover product variants, grouping and price rules; the pricing module provides currencies, regions, tiers and conditional price lists. This is a credible middle path between writing every commerce primitive and buying a complete channel platform. It does not establish fit for NRC/MRC contracts, technical BOM validation, immutable approved quotes or partner/solution isolation. If selected, use its supported module/API boundary behind the commercial authority; do not let a second price calculator compete with an authoritative CPQ. Prove renewal terms, protected costs and price-version reproducibility. [Product module](https://docs.medusajs.com/resources/commerce-modules/product), [Pricing module](https://docs.medusajs.com/resources/commerce-modules/pricing).

**CloudBlue Commerce/Connect:** Commerce documents partner/reseller storefronts, product onboarding, catalog and billing; Connect exposes REST integration and catalog syndication. These are credible paid candidates absent from the draft comparison. Commerce and Connect are distinct scopes: a marketplace metadata API is not proof of complete quoting or storefront automation. This route becomes attractive if supplier distribution, reseller tiers and subscription operations are near-term requirements; it may be disproportionate for a narrow selection-only pilot. Require an itemized scope and price, actual portfolio coverage, HubSpot coexistence, identity federation, regional rights and an export demonstration. Do not import a billing/order master merely because the vendor includes one. [Commerce scope](https://catalog.cloudblue.com/extensions/cloudblue-commerce/), [Integration surfaces](https://www.cloudblue.com/integrations/), [Connect catalog](https://connect.cloudblue.com/community/modules/catalog/).

**Decision-changing test:** load the same 20 authorized offers into each shortlisted route. Show two partners with different visibility and prices; revoke one offer; preserve a historic quote; compare products; export a canonical selection; hide costs from a partner; and demonstrate recovery and export. Measure catalog onboarding labor as well as software implementation. If a purchased route cannot demonstrate rights and tenant boundaries, exclude it regardless of its storefront appearance.

## Quote and proposal authority

**HubSpot current Quotes API:** the current guide requires a qualifying Revenue Hub subscription, distinguishes current quotes from legacy quotes, requires line item/contact/deal associations, and says approval states are primarily controlled by UI/workflows. It also documents unsupported quote-level adjustments/payment schedules while allowing line-item discounts and taxes. Therefore, prove the actual account, API version and approval journey; do not assume a fully headless approval flow or use legacy examples as evidence for current quoting. These documented limits do not themselves prove the required NRC/MRC cases fail. [Current Quotes API](https://developers.hubspot.com/docs/api-reference/latest/crm/objects/quotes/guide).

The template guide distinguishes code-customizable legacy themes from the current standardized template system. Test the proposed 20-page solution document, diagrams, site grouping and internal-cost suppression before selecting HubSpot as both quote authority and renderer. An external renderer can remain possible if it consumes authoritative approved data and does not recalculate commercial totals. Current and older documentation use different product packaging labels; the account subscription and contracted entitlement are decisive. [Template distinction](https://developers.hubspot.com/docs/cms/start-building/building-blocks/themes/legacy-quote-themes), [Approval setup](https://knowledge.hubspot.com/quotes/set-up-quote-approvals).

**QuoteWerks Web:** its documented HubSpot integration can read customer records, create/link deals and map quote items. It exposes controls for deal completion, amount selection and bundle summaries. This is a meaningful commercial alternative, not a proposal to replace HubSpot. However, the setup lists broad CRM permissions; review least privilege and partner access rather than granting every partner equivalent CRM rights. Disable automatic deal-won behavior unless Commercial explicitly selects it. Verify supported automation/API rights, native SSO, protected cost fields, quote version audit, multisite grouping, recurring lines and exit. A connector brochure is not proof of a partner-facing service contract. [HubSpot integration and configurable behavior](https://info.quotewerks.com/knowledge-base/how-do-i-setup-the-hubspot-crm-integration).

**ERPNext:** its quotation workflow includes items, pricing and transaction terms, so it merits comparison when the organization also needs an ERP-backed commercial lifecycle. Adopting it solely for a quotation screen can introduce competing customer/product masters and substantial operations. Keep HubSpot authoritative for agreed CRM fields; scope any ERPNext role explicitly. Validate NRC/MRC, partner access, approval snapshots, supported APIs, upgrade extensions and export. [Quotation documentation](https://docs.frappe.io/erpnext/quotation).

**Custom quote authority:** strongest control over solution semantics, reproducible technical checks and immutable approvals, but highest responsibility for commercial correctness, rule administration, audit, document generation, amendments and maintenance. Do not choose it solely because the initial ten cases are easy to code. Keep technical validation distinct from price evaluation so it can serve either a bought or built quote authority.

**Ten minimum comparison cases:** fixed hardware NRC; recurring service MRC and term; combined NRC/MRC; partner-specific price visibility; volume tier; authorized discount and margin restriction; country/currency/tax treatment; 60-site expansion with overrides; price expiry and revision after approval; and rejected technical dependency with a corrected resubmission. Each must demonstrate exact expected totals, actor authority, traceable source/rule versions and an unchanged historical quote. Add a timeout-after-success test, a revoked partner grant and a proposal-template test. The commercial owner supplies expected answers; the vendor does not grade its own calculator.

**Provisional direction:** test HubSpot first and QuoteWerks as a concrete challenger. Keep ERPNext conditional on a wider commercial-system need. Select custom only after documented fit failures or a defensible three-year cost/ownership advantage. Never allow two systems to issue authoritative totals for the same quote version.

## Floor Plan

**Hamina:** documented import/export through OpenIntent supports a practical file handoff. It is lossy: survey measurements are excluded, and its support matrix omits items including switch total ports/power budget, floor alignment and some other geometry/context. Exported data must carry fidelity warnings; canonical product specifications and reviewed evidence must supply missing facts before technical validation. Do not call a successful ZIP import proof of a complete design round trip. [OpenIntent support matrix](https://docs.hamina.com/hamina/live/openintent).

Its account guidance requires named users and prohibits shared logins. Published reporting supports PDF and interactive links, with optional password protection. These facts affect partner licensing and access control: an unprotected report URL is not an acceptable substitute for a tenant-authorized artifact route. Enterprise federation, headless automation and embedding rights remain unverified. Region documentation is inconsistent about whether user accounts are shared between EU and US instances; obtain a vendor-confirmed identity/data residency statement. [Accounts and licenses](https://docs.hamina.com/hamina/other/accounts-licenses), [Report sharing](https://docs.hamina.com/hamina/reporting-sharing/reporting), [Instance introduction](https://docs.hamina.com/hamina).

**Custom geometry editor:** reasonable for calibrated placement and BOM generation; not evidence of reliable RF predictions. Budget geometry/file support, revisions, object authorization and export. Buy specialist RF computation unless validation requirements and long-term maintenance justify building it. The draft's canvas-library alternative is not equivalent to a specialist planning product.

**Provisional direction:** Hamina proof of fit before bespoke RF work. Compare any incumbent specialist planner already licensed by the organization; this review could not verify Ekahau's current integration contract, so no support/API claim or score is assigned. Test one representative floor plan with APs, wired devices, scale, multiple floors and canonical products. Quantify exported and lost fields, accuracy evidence, operator steps and license cost per active designer. Separate Wi-Fi coverage from camera field of view, IoT and edge-compute sizing: one successful RF test does not cover all requirements on PDF pp. 6–7.

## Discovery

**runZero:** documents organization-scoped export and read/write APIs, tier-dependent capabilities and account-wide administrative surfaces. Prefer the smallest scoped export credential for ingestion; do not use a global account credential merely for convenience. Its export documentation says CSV lacks some nested detail that JSON preserves, so select and test the format deliberately. SAML integration is documented, but the single-domain requirements and role mapping need confirmation for the proposed partner population. [API scope](https://help.runzero.com/docs/leveraging-the-api/), [Export fidelity](https://help.runzero.com/docs/exporting-asset-data/), [SSO requirements](https://help.runzero.com/docs/implementing-sso/).

Vendor organizations provide an access boundary; they do not demonstrate the independent deployment, restore or failure boundaries required by EA for detailed solution state. Obtain a supported deployment/tenancy model and any required exception before accepting a shared SaaS organization model. [Organization model](https://help.runzero.com/docs/organizations/).

**Inventory imports/NetBox:** distinguish observation collection from intended inventory and configuration authority. Adding a NetBox store is worthwhile only when its inventory functions are needed and its role is reconciled with the existing iTop decision. An import pipeline can satisfy a deliberately limited assessment pilot without introducing another detailed master. This does not satisfy active scanning. NetBox describes itself as a network source of truth; that is not the same role as the portal's transient observation assessment. [NetBox introduction](https://netboxlabs.com/docs/netbox/introduction/).

**Custom scanner:** highest device/protocol maintenance and operational safety burden. Even a familiar scanning tool has distribution and embedding terms to assess; do not assume “free download” permits incorporation into a commercial appliance or service. [Nmap published terms](https://nmap.org/book/man-legal.html). Procurement must obtain the applicable rights; this review is not a legal determination.

**Provisional direction:** compare runZero with an existing customer-approved collector plus a minimal importer. Prove authorized target restriction, kill switch, local credential handling, duplicate/reordered batches, disconnected recovery and reviewed KEEP/REUSE/UPGRADE/REPLACE/ADD. Measure device identification coverage against a known lab inventory, including unknown devices and unsupported protocols. Never infer a reused device is commercially or technically acceptable merely because it was discovered.

## AI Solution Builder

**Managed inference with owned orchestration:** avoids operating model-serving capacity while preserving domain tools, retrieval entitlement, grounding evaluation and human approval in the service. Bedrock documentation defines a shared-responsibility boundary and model-provider access restrictions; those facts do not eliminate review of provider/model-specific retention, abuse monitoring, inference routing, logging and residency. Inspect those settings for the exact selected model and deployment. [Bedrock data protection](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html).

**vLLM plus separately licensed model weights:** useful when control, locality or measured sustained utilization justify model operations. Serving software alone does not provide a secure multitenant solution builder. Its security guide identifies endpoints not protected by its API-key option; protect the complete serving boundary, restrict egress and media fetching, isolate caches/context and govern model artifacts. Budget GPU capacity, patching, load shedding, model evaluation, rollback and on-call operation. [vLLM security](https://docs.vllm.ai/en/latest/usage/security/).

**Provisional direction:** compare managed inference and self-hosted inference behind the same owned service/tool interface. Use the same 50 domain cases plus adversarial/revocation cases, report grounded correctness, unauthorized-action rate, latency and cost per accepted solution. The choice is not “buy an LLM versus build all AI”: ngenious still owns the solution workflow and its authorization in both cases. A generic agent platform should be evaluated only if it demonstrably reduces that work without gaining direct table writes or commercial approval authority.

## Multi-Site Designer

The differentiating work is versioned profiles, site overrides, reusable floor-plan/assessment inputs and deterministic expansion into canonical BOMs. The researched commerce/quoting documentation does not establish an out-of-the-box fit for those semantics. This is a conditional reason to favor a thin custom independent service, not proof that no purchased product could fit.

Give the selected planning and CPQ candidates the same test: import 60 sites; apply a profile to 40; override one site; change the profile; preview the diff; repeat the command; verify per-site and aggregate quantities; roll back; and show a historical approved quote remains unchanged. If an extension can do this through supported APIs without sharing internal schemas or requiring simultaneous releases, compare extension cost against custom. Preserve native service access in either route.

## Shared infrastructure and reporting

**Identity:** consume ngenious SSO first. The SSO repository selects Keycloak conditionally on its own production checks and assigns authorization to applications. A Partner-Portal procurement comparison must not restart enterprise identity selection. Auth0 or another IdP is an exception/enterprise capability decision, not a convenient portal-local alternative. See the exact SSO baseline in the companion review.

**Runtime:** compare the incumbent managed container platform, AWS ECS/Fargate, and Azure Container Apps against the approved region, network, secrets, deployment and recovery model. AWS documents task isolation; Azure documents revision management, jobs and scaling. Neither service by itself supplies independent database recovery, queue policies or a funded operator. Avoid a new Kubernetes platform unless demonstrated requirements and an existing operating team justify it. [Fargate architecture](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), [Container Apps capabilities](https://learn.microsoft.com/en-us/azure/container-apps/overview).

**Data:** application/database roles and PostgreSQL RLS are useful defense in depth, not substitutes for a declared solution boundary. PostgreSQL documents owner/superuser bypass behavior. Prove migration/backup/support access and pooled connection context as well as ordinary API requests. [RLS behavior](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

**BI:** compare a small owned reporting projection with a bought embedded BI route before deploying a general analytics platform. Power BI documents RLS, object security and workspace isolation; it also distinguishes embedded effective identity from ordinary service-role assignments. Test exports, caches, scheduled jobs and service-principal access, not just the visible dashboard. Apache Superset remains a candidate requiring its own security/operating evidence; this research did not verify its current configuration contract sufficiently to endorse it. A CSV renamed as Excel or a screenshot in PowerPoint is not proof of the requested report formats. [Power BI embedded security](https://learn.microsoft.com/en-us/power-bi/developer/embedded/embedded-row-level-security).

## Cost and procurement evidence

License screening is edition-specific. Medusa's current repository license identifies MIT-covered code and a separate Enterprise Edition carve-out; do not label every optional capability MIT. ERPNext publishes GPLv3 terms, while NetBox and vLLM publish Apache-2.0 terms. Pin the actual release, included extensions and model weights before evaluating distribution/service obligations. None of these licenses establishes commercial support, SSO integration or customer isolation. [Medusa license](https://github.com/medusajs/medusa/blob/develop/LICENSE), [ERPNext license](https://github.com/frappe/erpnext/blob/develop/license.txt), [NetBox license](https://github.com/netbox-community/netbox/blob/main/LICENSE.txt), [vLLM license](https://github.com/vllm-project/vllm/blob/main/LICENSE).

Use a common three-year model:

`TCO = implementation + integration + migration + 36 × (licenses + cloud + support + stewardship + operations) + upgrades + assurance + exit`.

Calculate low/base/high scenarios for two pilot partners and the proposed ten-partner load fixture. Separate internal staff seats, external designer/partner seats, scanned assets, API quotas, inference tokens, storage/export and support tiers. Include operator time for manual handoffs and data mapping; free software does not make those costs zero. Use contractual prices and loaded labor rates supplied by the owners. No monetary winner can be declared from the evidence currently available.

For each shortlisted vendor obtain a reproducible demonstration, permitted-use/license statement, SSO and API entitlement, data-processing/residency terms, deletion/backup behavior, incident notification/support terms, version/deprecation policy and export sample. Identify one accountable owner and an exit estimate. Obtain explicit approval before trials requiring spend, external account changes or real/customer data. Desk research and documentation refinement can proceed within the existing authorization.
